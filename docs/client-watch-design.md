# クライアントSlack依頼検知（client-watch）設計メモ

- 起案: 2026-07-29 戸田さん（Claude Codeセッションでの構想・壁打ち済み）
- 状態: 設計合意ドラフト（未実装・未起票）。実装は**別チャット（新セッション）**で行う
- 対象リポジトリ: `masaki-lipple/hermes-chiaki`（Chiaki AIの機能として開発する＝戸田決定）

## 1. 目的

クライアントのSlackワークスペース（別WS）での「依頼」を検知し、自社（Lipple）側の対応が
流れの各段階で止まっていないかを追跡・リマインドする。タスクの管理そのものは既存の別AI
（GCPタスクAI）が担う＝Chiaki AIは**観測と催促**に徹する。

対象とする業務フロー（戸田定義）:

```
先方がいってくる → 返信をする → サブタスクをつくる → 実行 → 先方にかえす
```

## 2. 3チェックポイントのステートマシン

クライアントの依頼スレッド1本につき1エントリを台帳（client_requests.jsonl 想定）で管理し、
3つのチェックポイントを順に検証する。

```
先方の依頼 →①返信ある？→②タスク化された？→（実行）→③先方スレッドに報告した？
              ↓なし         ↓なし（「やります」型）        ↓なし
        「返信してください」 「タスク化してください」  「先方に報告してください」
```

- ①返信: クライアントスレッドに**自社メンバーの返信**があるか（「やります」と返しただけの
  ケースを②で拾うため、返信の有無とタスク化は別チェックポイントにする＝戸田指摘）。
- ②タスク化: 自社タスクチャンネルに対応するタスクが作られたか。
- ③完了報告: タスク完了後、**クライアントの該当スレッド**に報告が返されたか。

### 突合の設計（この機能の肝）

- **②の対応付けは「Chiaki AIの検知通知スレッドを錨にする」**: 検知時に自社タスクチャンネルへ
  出す通知投稿に対し、担当者が ✅リアクション または タスクURLの返信 で「タスク化済み」を宣言する
  運用にする。クライアントスレッド↔自社タスクの曖昧なマッチング（LLM推測）をしない＝決定論で追跡。
- **③の完了検知**: タスク管理は別AIのため、自社タスクチャンネルの完了状態（kanryoリアクション等・
  既存task-followが読んでいる形式）を流用。完了後にクライアントスレッドへ自社メンバーの投稿が
  あるかを検証し、無ければ「先方に報告してください」。
- **①の返信済み判定に必要な設定**: 自社メンバーのクライアントWS側ユーザーIDの対応表
  （roster設定ファイル。クライアントWSごとに管理）。

## 3. アーキテクチャ

- **クライアントWS用に専用Slackアプリを新規作成**（Manifestから・前例あり）。
  **read-onlyスコープのみ**（channels:history, channels:read 等）＝クライアント側への誤投稿が
  構造的に不可能。発話はすべて自社Slack側で行う。
- クライアント管理者にアプリのインストールと対象チャンネルへの招待をしてもらう。
- 検知はcron（15分毎目安）のポーリング＝既存の決定論設計と整合（listener不要・別WSのSocket Mode常駐を増やさない）。
- 検知判定: 決定論プレフィルタ（依頼らしい表現・宛先・疑問/依頼文型）＋LLM分類（Haiku/GPT）。
- 通知: 自社タスク投稿チャンネルへ「クライアント◯◯で依頼を検知しました。返信とタスク化をお願いします」
  ＋要約＋元リンク＋担当者メンション。
- リマインド: 営業時間内・上限付き（task-followと同じ型）。チェックポイント別の文面。
- 学習: 「これは依頼じゃない」の却下を reject_learn の型で学習し再検知しない。
- 多WS対応の土台: lib/source のトークンをワークスペース文脈で切り替えられるようにする
  （client_workspaces 設定: ws名→トークンenvキー・対象チャンネル・roster）。トークンは .env（repo外）。

## 4. 段階導入（戸田合意済みの方針）

1. **Phase 1**: read-onlyアプリ雛形＋多WS土台＋検知→自社通知のみ（リマインドなし）。
   1〜2週間、精度（誤検知率）を観測する。誤検知でチームにリマインドが飛ぶのが一番信頼を削るため。
2. **Phase 2**: ①②③のチェックポイント検証＋リマインド有効化（上限付き・営業時間内）。
3. **Phase 3**: 精度改善（却下学習・クライアント別ルール）・複数クライアント展開。

## 5. 決めること（戸田さんボール）

- 1社目のクライアント（識別名・対象チャンネル）
- 通知先の自社タスク投稿チャンネル
- 通知時にメンションする担当者（固定か、クライアント別か）
- 自社メンバーのクライアントWS側ユーザーID（roster用・後ででも可）
- クライアント側へのアプリ設置の段取り（管理者への依頼）

## 6. 制約・前提（既存の決定との整合）

- クライアントの会話内容を自社VPSで処理し一部（要約＋リンク）を自社Slackへ転記する＝
  クライアントとの契約・信頼関係上の可否は戸田さんが判断（2026-07-29時点で了承前提の構想）。
- コード変更・Codex起動につながる操作の受付は戸田さんのuser ID（U9R35H06L）ゲートを維持。
- 「未承認は本番不反映」のHITL原則はこの機能では緩めない（Chiaki AIが勝手にクライアントへ
  発話しない＝そもそも書き込み権限を持たない）。
- 発話ゲート・出口台帳・約束台帳（整合パック・2026-07-29導入）はこの機能の通知・リマインドにも適用される。

## 7. 実装時の入口（新セッション向けメモ）

- 通知・リマインドの投稿は lib/source 経由（出口台帳・レギュレーション適用が自動で効く）。
- リマインドの型は profile/skills/lipple/task-follow を参照（営業時間・上限・冪等ガード）。
- 却下学習は reject_learn.jsonl の型（apply-ruling/typo-scan/propose-to-approvalの実装参照）。
- 検知台帳は「1依頼スレッド=1エントリ・状態遷移」で、exec_ledger（追記型・新しい行が勝つ）
  ではなく pending_approvals 型（items辞書＋ロック）が向く。
- Slackアプリ Manifest の前例: `deploy/chiaki-ai-app-manifest.yaml`（スコープをread-onlyに絞る）。
